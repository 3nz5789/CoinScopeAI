# Phase 1 Charter — Strategic Foundation

**Owner:** Founder / Strategy Chief of Staff
**Phase window:** May–early Jul 2026 (overlaps P0 Validation Cohort and tail of P0 → start of P1 Narrow Ship)
**Sits on top of:** v1 framework LOCKED 2026-05-01 (`/business-plan/00-framework.md` + `_decisions/decision-log.md`)
**Last updated:** 2026-05-04 *(charter amended — BRAND added as 7th workstream)*

---

## 1. Goal

Lock the **strategic foundation** for CoinScopeAI by closing the loop on seven workstreams that determine *what we sell, to whom, against whom, how we sound and look, with what risk envelope, and on what trust posture*:

1. **MARKET** — what category we are in, and what category narrative we ride.
2. **ICP** — which one of the three locked personas (Omar, Karim, Layla) is the primary execution target for P1.
3. **POSITIONING** — the one positioning sentence we lead every surface with, plus the things we explicitly do *not* claim.
4. **PRODUCT** — what the P1 Narrow Ship offer is, what it delivers, and what is deferred.
5. **TRUST** — which trust signals must be live before paid acquisition is ever turned on.
6. **RISK** — how the engine's risk envelope (PCC v2 §8 Capital Cap, 10x / 10% / 5% / 5 / 80%) shows up in the *business plan*, not just the engine.
7. **BRAND** — how the locked positioning sentence and trust posture are externalized into a writer-and-designer-facing guide so every surface reads as one company *(added 2026-05-04 via Path B amendment)*.

Phase 1 is **not** about closing GTM channel selection, pricing experiments, fundraising, or financial model build — those belong to Phases 2–4.

## 4. Exit criteria

Phase 1 is *complete* when **all seven** are true:

1. **MARKET** — One sentence category statement signed off by founder; documented in `01-market.md`. Two adjacent categories explicitly rejected with reason.
2. **ICP** — One of {Omar, Karim, Layla} is named **P1 primary**; the other two are **secondary / deferred** with the reason. Documented in `02-icp.md`.
3. **POSITIONING** — One positioning sentence + four anti-claim lines locked. Documented in `03-positioning.md`. Cross-referenced from app hero, docs, and Telegram bot intro.
4. **PRODUCT** — P1 Narrow Ship offer scope written as a one-page MOSCOW (Must / Should / Could / Won't) tied to existing engine endpoints. Documented in `04-product.md`.
5. **TRUST** — Minimum viable trust set (the 5–7 things that must be live before paid acquisition) documented in `05-trust.md` with owner + status per item.
6. **RISK** — `06-risk.md` cross-references PCC v2 §8 and explicitly states the *business-plan-level* claims allowed and disallowed at each risk-state (Validation / Narrow Ship / Vendor Expansion / Desk Full).
7. **BRAND** — Brand strategy summary, voice + tone guidelines, trust + credibility pillars, visual messaging rules, and do/don't patternbook documented in `07-brand.md`. De-dup register reconciled with POSITIONING and TRUST.

Plus: Phase 1 backlog (`08-task-backlog.md`) has every NOW task either Done or moved to a phase-2 backlog with reason.

## 5. Phase 1 risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| Premature positioning lock | Lock the wrong category and Phase 2 GTM burns months on the wrong message | Bound positioning to a *reversible* sentence; review at end of P0 cohort |
| ICP scope creep | Trying to serve all three personas in P1 dilutes product, copy, and support | Hard pick one; deferred personas get a single line, no roadmap promises |
| Trust theatre | Adding "trust signals" that aren't load-bearing (badges, vague claims) instead of audited claims | Every trust signal must be *verifiable* by a third party or by the cohort itself |
| Risk envelope drift | Marketing copy understates the gates; an outage or drawdown produces a credibility crisis | Every public risk number must trace back to PCC v2 §8 or the canonical 5 tokens |
| Competing with the locked framework | Phase 1 docs duplicate or contradict v1 framework section files | Phase 1 docs are *planning artifacts*, not strategy. They reference v1 section files and queue work against them |

## 9. How to read Phase 1 docs

- Each workstream scaffold (`01–07`) follows the same eight-block structure: purpose → why for CSAI → required subsections → recommended artifacts → assumptions → decisions → failure modes → tasks.
- `08-task-backlog.md` is the **execution surface**. Tasks named exactly `[TYPE] [AREA] — Action / Deliverable`. Grouped by area, ordered NOW / NEXT / LATER.
- `10-decision-register.md` lists only the decisions that block Phase 1 exit.
- `11-open-questions.md` lists only the questions whose answers Phase 1 needs.

For everything else (full plan structure, all phases, all workstreams), see the v1 framework and the eventual phase-2/3/4 charters.
